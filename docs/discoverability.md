# Discoverability — crawlable pages, previews and the sitemap

Owner document for how this product is found and how it appears when somebody
shares a link. Gate 3 in [`public-release-roadmap.md`](public-release-roadmap.md)
owns the release decision; this document owns how it works.

---

## 1. The problem a hash route creates

`CLAUDE.md` fixes routing as one hash: `#/<slug>` is a scene, `#/organs` is the
explorer. That decision is right for the application and wrong for everything
outside it, because **a crawler is never sent a fragment**. To a search engine,
a link preview or a sitemap, all twenty models are one URL with one title.

The fix is not to change routing. It is to give the outside world what it can
actually read.

## 2. What the build emits

Generated by `scripts/site-plugin.js` from `src/catalog/` — nothing is
hand-maintained, so a new scene still means one manifest entry and no more:

| Output | Contents |
| --- | --- |
| `dist/s/<slug>/index.html` | One page per **public** scene: title, description, maturity, review state, the educational-model boundary, and a link into the model |
| `dist/sitemap.xml` | Site root plus every scene page. Emitted only with `VITE_SITE_URL` |
| `dist/robots.txt` | Allow-all plus the sitemap reference |
| `dist/index.html` | Canonical, Open Graph, Twitter and `WebSite` JSON-LD injected into the app shell |

The scene pages need no bundle, no fonts and no JavaScript. That makes them the
most robust WebGL-independent surface in the product: a reader with a browser
that cannot start a renderer can still learn what a model is about and what it
does not claim.

## 3. Rules the generator keeps

- **Prototype work is not published.** Only `PUBLIC_SCENES` get a page or a
  sitemap entry. A Prototype scene deliberately makes no numerical claim, and a
  search result is exactly where that caveat is lost. There is no `Disallow`
  rule for it either: robots.txt matches paths, so a rule for `#/lab` would look
  like protection and provide none.
- **No guessed canonical.** Without `VITE_SITE_URL` the pages are still built,
  but canonical and Open Graph URLs are omitted and the sitemap is skipped. A
  wrong canonical is worse than none — it tells a search engine the real page is
  somewhere that does not exist.
- **No image is advertised unless it exists.** A preview that cannot load its
  image renders a broken card. The build lists by name every scene missing
  `public/social/<slug>.png` instead of pointing at a file that is not there.
- **The structured data does not overclaim.** Each page is a
  `LearningResource`, not a `MedicalWebPage`, and its topic is a plain `Thing`
  rather than a `MedicalCondition`. Describing the product to a search engine
  as clinical reference material would assert an authority the model cards
  explicitly decline. Every page carries the disclaimer in both languages.
- **Catalogue text is escaped, in markup and in JSON-LD.** A `</script>` inside
  a title would otherwise terminate the structured-data block and the rest
  would be parsed as markup, so `<`, `>` and `&` are unicode-escaped there.

## 4. Configuration

| Variable | Effect when unset |
| --- | --- |
| `VITE_SITE_URL` | Pages are built; canonical/OG URLs omitted and no sitemap |

It is set in [`../netlify.toml`](../netlify.toml) — in production
`https://med-3d-lab.necofindjob.com`, and deliberately empty for preview
deploys, which are not the site and so claim no canonical and emit no sitemap.
Set it to the deployment origin, with no trailing path unless the site is
served from a subpath (`https://example.org/lab`). Links from a scene page into
the app are relative (`../../#/<slug>`), so a subpath deployment works either
way.

**A trailing slash is not a second site.** The variable is typed by a person
into a deploy environment, and `https://site` and `https://site/` mean the same
thing to that person. The build normalises it once, so both spellings produce
the same canonical, the same Open Graph URLs and the same sitemap; the home
page's canonical is the site root (`https://site/`), which is the address the
sitemap's first entry gives it.

**The origin lives in the deploy, not in `src/`.** Moving the site is then a
deploy change rather than a code change — but the pages are generated at build
time, so a domain change takes effect only on a rebuild.

`npm run verify:site` checks the emitted output against itself: every page's
canonical, `og:url` and preview image must name the host the sitemap names.
That catches a generator emitting two different addresses for one site. It does
**not** catch a build made with a stale `VITE_SITE_URL`, because such a build
agrees with itself perfectly — every page and the sitemap name the host the site
has left, together. For that, the intended origin has to come from outside the
build:

```bash
npm run verify:site -- --origin https://med-3d-lab.necofindjob.com
```

And a domain that moved with no redeploy at all is not visible in any local
build, because the build is not what the public is being served. That takes a
request to the site itself:

```bash
npm run verify:live -- https://med-3d-lab.necofindjob.com
```

`scripts/check-live-site.mjs` fetches robots.txt, the sitemap, the home page,
every scene page and the preview card from the deployed origin, and fails if
what is served names another host, omits a canonical, has lost the sitemap, or
publishes a Prototype scene. It needs the live site, so it is not in CI; it is a
step in the deploy section and in the domain-change checklist in
[`release-runbook.md`](release-runbook.md#changing-the-primary-domain), which
also covers the rest of the move — Stripe's webhook endpoint, Supabase's
redirect allowlist, redirects from the old host.

## 5. Social cards

Link previews want a 1200 × 630 raster, and `npm run cards` draws one per
public scene plus one for the site.

### They are committed, not built

A link preview is a static asset a crawler fetches once and caches for weeks,
and there are ten of them that change perhaps twice a year. Making every build
download a browser to redraw them is the wrong trade, and adding a rasteriser
to `dependencies` would break the rule that keeps the build honest (`three` and
nothing else). So Playwright is installed on demand, exactly as it is for the
viewport matrix, and the PNGs live in `public/social/`.

The cost of not building them is that they can go stale, so `npm run cards`
also writes `public/social/cards.json`, recording the digest of the markup each
PNG was drawn from. `npm run cards:check` recomputes that from the catalogue —
**with no browser at all** — and fails when a title, a maturity, a review state
or a description has moved on without the card.

Comparing the *images* was the first design and it cannot work: they are drawn
with the fonts of whichever machine drew them, so a CI runner with a different
font set would fail every pull request, including the ones that changed
nothing. A check that fails for a reason unrelated to the change is a check
people learn to ignore. What is comparable on any machine is what the card was
asked to say.

### Why they are typography and not a picture of the model

A screenshot of the 3D scene was the obvious thing and was tried first. Two
problems:

- **It cannot be reproduced.** There is no GPU in CI, and a software-rendered
  frame is not what a reader with a GPU sees. The committed card would be a
  picture of something nobody has.
- **A scene frame carries no maturity and no review state**, which is exactly
  what this product has decided a reader is owed *before* they click. A card
  that says `Reviewed · レビュー済` next to `Re-review required · 再レビュー必要`
  — which is what COPD's card says, because that is true of COPD — is doing the
  Trust surface's job at the moment the decision is being made.

Every card also carries the educational-model boundary in both languages,
because a card travels without the page it came from.

### The description length is measured, not tabulated

The card is a fixed 630 px and the boundary line at its foot may never be
pushed off it, so the description is what yields. How much it has to yield
depends on how many lines the English title takes, how many the Japanese
subtitle takes, and where the text happens to break — three things a character
count models badly. The first attempt keyed the budget on the English title
length and clipped COPD and portal hypertension, whose titles are short and
whose Japanese runs long.

So the rasteriser starts at `BODY_BUDGET.start` and shortens until the browser
says the card fits. The result is deterministic, and the run prints what each
card settled on.

The check that guards this was itself wrong once, and it is worth recording
why: it asked whether anything ran past the bottom edge — which the card's own
`overflow: hidden` had already made impossible. It could never fire, and was
caught by deliberately making a card far too tall and watching it pass. It now
asks whether the clip *did anything*.

### Fonts

No webfont: a generator that reaches the network draws a different image on a
different day. The consequence is honest and worth writing down — regenerating
the cards on a machine with different fonts produces slightly different images.
That is the other reason they are committed rather than built, and the reason
`cards:check` compares content rather than pixels.

## 6. Checked in CI

- `tests/site-metadata.test.js` — the generator's output: escaping, canonical
  behaviour, sitemap contents, structured-data typing, and that no Lab scene is
  ever listed.
- `npm run verify:site` — that the build actually emitted it. A plugin that
  silently stops running is the failure nobody notices until a preview is blank
  weeks later. Not in CI, because it needs the deployed site: `npm run
  verify:live -- <origin>`, which asks the published site the same questions.
- `tests/social-cards.test.js` — what a card says, and that the committed set
  matches the public catalogue.
- `npm run cards:check` — that the committed rasters still match the catalogue
  they were drawn from.

## 7. The brain launch (2026-11-24) — what changed, and the plan for topic pages

**What changed now.** The site's title, description, Open Graph tags and
JSON-LD read `src/data/brand.js`, so they followed the rename to 3Dモデルラボ
without an edit here. The published set is two scenes — `brain-anatomy` and
`mri-atlas` — so the build emits `/s/brain-anatomy/` and `/s/mri-atlas/`, and
the sitemap lists those and the root. **The four pages of the scenes the
launch withdrew (`/s/heart-anatomy/`, `/s/lung-anatomy/`, `/s/liver-anatomy/`,
`/s/cardiac-output/`) are no longer emitted and will answer 404.** No redirect
is configured: sending a reader who searched for the heart to a brain page is a
worse answer than "not here" (F-288 holds the decision).

`mri-atlas` carries the search terms a learner would use as catalogue
`conditions` (脳MRI・MRI解剖・断面解剖・軸位断・冠状断・矢状断・標準脳・MNI152),
which the scene page prints.

**What is not crawlable yet, and should be.** The launch's most searchable
subjects are below the scene level, and a hash query is invisible to a crawler:

| Subject a person searches | Where it lives today | Crawlable? |
| --- | --- | --- |
| 海馬 MRI、尾状核 位置、… (a structure) | `#/mri-atlas?structure=hippocampus-l` | No — one page for 102 structures |
| 失語、記憶、半側空間無視、遂行機能 (a theme) | `#/functions?theme=language` | No — and the page is questions only |

**The plan, not built in this change:**

1. **Structure pages** — `/s/mri-atlas/<structure>/`, one per *bilateral*
   structure (51, not 102), generated from `public/assets/mri/atlas.json` and
   `src/data/mriAtlas.js`: both names, the group, the note where there is one,
   the MNI coordinate of the interior point, a static rendering of the three
   planes at that point, and a link that opens the atlas on it. Everything on
   such a page is anatomy the published scene already states, so it needs no
   new publication decision — but the static images are new derived assets and
   belong in the asset manifest.
2. **Theme pages** — `/s/functions/<theme>/`. **Only after the function model is
   published.** A theme page that ranked for 「失語」 would have to say something
   about aphasia, and what this product may say about aphasia is exactly what
   the closed model's review governs (R-2026-11-24-02). Until then the theme
   exists as a question on `#/functions` and nowhere a crawler reads.
3. **Per-structure link previews** are not planned: 51 more committed images
   for a marginal gain.

Both are recorded as F-280.
