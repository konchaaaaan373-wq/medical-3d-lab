### F-20 パスワード再設定の実地確認 — P1（ドメイン切替）

Supabase の Site URL / Redirect URLs は新 origin
（`https://med-3d-lab.necofindjob.com`、`/**` 付き）に更新済みで、再デプロイ後に
認証 UI が出ることも確認しました。**ただしメールを受け取る往復は未実施です。**
ここは自動チェックが構造的に届かない唯一の箇所で（受信箱が要る）、
壊れていても誰も報告してくれません。

- 確かめ方: ログアウト状態（シークレットウィンドウが早い）でナビ右上の
  `○ ログイン` → メールアドレスを入力 → `Forgot password? / パスワードを忘れた`。
  届いたリンクが `https://med-3d-lab.necofindjob.com/?account=recovery` に着地し、
  「新しいパスワードを設定」フォームが出ること。
- 完了の定義: 上記が通り、実際に新しいパスワードでログインできる。
- **2026-09-12 の変更点**: 受信箱が要る部分**以外**は自動化しました。
  `npm run verify:auth` が、Supabase の implicit-flow フラグメント
  （`#access_token=…&type=recovery`）での着地、トークンが即座に URL から
  消えること、「新しいパスワードを設定」フォームが出ること、Enter で
  `PUT /auth/v1/user` に届くこと、そして**再設定の途中でリロードしても**
  （`?account=recovery` と、フラグメントが保存したセッションを頼りに）
  同じフォームが出ることを実測します。**2026-09-14 追記**: クエリのフラグは
  それを発行したセッションより長く残る（ブックマーク・復元したタブ・
  1 時間前のリンク・単に URL を打った人）ので、セッションが無いときは
  フォームを出さず「有効期限が切れています」と言うようにしました。
  フラグがルートを上書きすることもありません——シーンを開いたまま
  リロードしても、そのシーンの上にダイアログが出ます。
  再設定フォームも `<form>` になり Enter で送信できます。
- **残っているのは「メールが実際に届くか」の 1 点だけです。** リンクの着地先は
  上記が担保するので、確認すべきは受信と、リンクに載る origin が
  `https://med-3d-lab.necofindjob.com` であることの 2 点に縮みました。
- **F-98 で判明（2026-09-13）: `Confirm email` は ON です。** つまり確認メールも
  再設定メールも、どちらも同じ Supabase の送信経路を通ります。**片方が届かなければ
  もう片方も届きません**——逆に言えば、確かめるべきは「このプロジェクトがメールを
  送れているか」の 1 点です。
- **無料プランの組み込みメール送信は本番向けではありません。** Supabase の
  built-in email service は開発用で、送信レート制限が厳しく設定されています。
  この組織は `FREE` プランなので、**ここが F-20 の最有力の失敗原因**です。
  確認する場所: Authentication → **Rate Limits**（送信上限）と、
  Project Settings → **Auth** の Custom SMTP（本番では独自 SMTP を設定するのが前提）。
- ここだけは受信箱が要るため自動化していません。**認証サービスに送信させるのは
  実在の人の受信箱への副作用**なので、検証スクリプトは GET しか行いません。

### F-45 胆道閉塞・アカラシアの臨床レビュー — P1（病態の量産）

#### 3 巡目（2026-09-14、拡大時にモデルが流れる）

所有者が動画で報告。**拡大するとモデルが右上へ流れ、ヘッダーと右パネルの下へ
入り込む。**（動画はこの作業環境には添付されておらず、見ていません。以下は
報告の記述から症状を実ブラウザで再現し、測った結果です。）

**原因は拡大処理ではなく、拡大の支点でした。** 1280×800 で測ると：

| | 距離 | `controls.target` の画面位置 | 被写体中心の画面位置 |
| --- | --- | --- | --- |
| 初期 | 4.758 | (640, 400) = 画面中心 | (463, 431) |
| 5 段ズームイン | 2.379（½） | (640, 400) 不動 | (286, 462) |

`fitPoseToSafeArea` は、パネルが残す帯に被写体を置くためにカメラと target を
**一緒に**平行移動します。構図としては正しく、その結果 **target は被写体の
いる場所ではなくなります**——実測で 177px 離れていました。`OrbitControls` の
既定のドリーは camera→target 上を進むので、止まって見えるのは target だけ。
被写体と target の距離は world 座標では一定なのに、フレームの半分の高さは
距離に比例して縮むので、**画面上のズレは拡大率ぶんそのまま拡大**します
（距離半分 → ズレ 2 倍。実測どおり）。数段でヘッダーの下へ出ます。

だから直し方は「中央へ戻す」ではなく、**支点を読んでいる場所に移すこと**です。

- **ポインタ／ピンチ** — `controls.zoomToCursor = true`。three.js の
  `_updateZoomParameters` が wheel ではポインタ座標、ピンチでは 2 本指の中点を
  支点にします。`enablePan = false` とは独立に効きます
- **ボタンと +/− キー**（支点になるポインタが無い）— 新しい `dollyAboutNdc()` が
  **表示帯の中心**を支点に camera と target を一様スケールします。向きは変わらず、
  距離だけ倍率どおりに変わるので、逆方向の同量で厳密に元へ戻ります
- **どちらもモデルを読みません。** bounding box の再計算も再フレーミングも
  ありません。`zoomToCursor` は支点を保つ結果として `controls.target` を動かしますが
  ——ポインタ下の点を固定することは数学的に軌道中心を動かすことなので——
  モデル由来の再計算は一切しません
- **大きく外れたときだけの最小補正** — `shiftIntoBand()`。帯の中に被写体が
  ある程度でも残っているうちは**何もしません**。ほぼ見えなくなったときだけ、
  外れている軸だけを、見える所まで最小限動かします。中央へは戻しません
- **全体表示／リセット**は従来どおり `fitPoseToSafeArea`——固定 UI を除いた
  表示領域の中央へ戻します（変更なし）

修正後の実測（ボタン 5 段・ホイール 4 段、いずれも減衰が収まるまで待って測定）:

| | 1280×800 | 390×844 |
| --- | --- | --- |
| 被写体上で拡大 → 被写体のズレ | **0px** | **0px** |
| 部位にポインタを置いて拡大 → その部位のズレ | **0px** | **0px** |
| 拡大 → 同量縮小 → 元構図とのズレ / 距離比 | **0px** / 1.000 | **0px** / 1.000 |

回帰は 2 か所で見ます——`tests/zoom-anchor.test.js`（支点の算術と、
**不具合そのものを再現するテスト**：支点を target にすると距離半分でズレが
2 倍になることを assert しているので、「中央固定」で直そうとすると落ちます）と、
`verify:anatomy` の実ブラウザ計測（本物のホイールと本物のポインタで上の 5 項目、

### F-40 溝のラベルが左外側ビューで出ない — P2（B3、2 手試して保留）

ことの帰結だと確認できました。安全側（出さない）に倒れるので放置可能ですが、
解決は下の (a)(b) のままです。

- 次に決めること（実装前に決める）: **(a)** 構造の複数点をサンプルして

1. **`position` を毎回 `clone()` して返すシーンのラベルは動きません。**
   腸閉塞シーンでは閉塞部のラベルが最初の部位に貼り付いたままになり、
   「移行部」というラベルが別の場所の腸を指していました。
   回避策として、シーン側が**同じ `Vector3` を持ち続けて中身を書き換える**形に
   しました（`BowelObstructionScene#updateAnchors`、
   `BenignProstaticEnlargementScene#updateAnchors`）。
2. **状態によって現れるラベルは、構築時の状態にしか従えません。**
   構築時に存在しなかった注釈は、その後どれだけ状態が変わっても生成されません。

どちらも回避はできていますが、**これはシーン側が知っているべき規約ではありません。**

- 決めること: `labels.setAnnotations()` のような入れ替え口を足すか、
  `getAnnotations()` の契約を「同一オブジェクトを返し続けること」として明文化し、

### F-133 開いた直後の構図と、「表示をリセット」後の構図が違った — **再オープン**（2026-09-16）/ P2

**2026-09-16、修正を撤回しました。副作用が元のバグより悪かったためです。**

入れた修正は許容値 `max(1e-3, distance * 0.005)` で、根拠は「意図的な zoom の
最小刻みよりはるかに小さい」という**推論**でした。測ったら違いました——
ホイール 1 刻みは damping 越しに徐々に効くので、**zoom の начало では
カメラはまだ直前の shot から 0.5% 以内**にいます。その瞬間に band が変わると
watcher は「読者は触っていない」と判定し、カメラを新しい構図に吸着させて
**読者の zoom ごと持っていきます**。

実測（`verify:anatomy --scene brain-anatomy`、390x844）:

| | zoom で被写体が動いた量 | 戻したあとの残差 |
| --- | --- | --- |
| `origin/main` | — （`exit=0`） | — |
| この修正あり | **20px** | **17px** |
| この修正を戻すと | 0px（`exit=0`） | 0px |

チェックは anchor が効いていれば**ちょうど 0px** を期待します。20px は誤差では
なく「anchor が無い」という意味です。`origin/main` を worktree に出して同じ
drive を回し、main が綺麗であること＝原因がこちらであることを確認しています。

- **元のバグは実在します。** 厳密比較は damping が残す 0.00125 を
  「読者が動かした」と読むので、再構図が毎回計算されては捨てられます
- どう直すか: **「最後に置いた場所からの距離」以外の所有判定**が要ります。
  その量は damping でも zoom 開始時でも小さく、**両者を分ける閾値は存在しません**。
  ポインタ操作が始まったかどうかを控えるほうが筋です
- 完了の定義: `verify:anatomy` の zoom 4 件が 0px のまま、かつ
  開いた直後と reset 後の構図が一致すること。**両方を同時に測ってから閉じること**


**同じシーン・同じ視点なのに、読み込み直後とリセット後でモデルの大きさが
違いました。** 原因は 2 つで、どちらも実画面を見て測って分かりました。

**1. 再フレーミングが、自分の番人に捨てられていた。**
`#ui` が印を付けられるとコンソールが全幅カードから隅の小カードに変わり、
帯が戻ります。それを見て撮り直す watcher は前からありましたが、
「読者がカメラを触っていないか」の判定が
**ワールド単位で 1/1000 以内**を要求していました。`controls.update()` は
damping つきで毎フレーム走り、置いた場所にビット単位では戻りません——
鼻で実測 **0.00125**。つまり毎回「読者が動かした」と判定され、
**計算した構図をそのまま捨てていました**。距離に対する割合（0.5%）に
変えています。

**2. 隅に寄ったコンソールを、帯から差し引いていなかった。**
`.console` は「フレームの中央を横切るか」で判定していたので、
全幅カードのあいだは差し引かれ、隅のカードになった瞬間に 0 になります。
被写体は rail が残した帯の左側に置かれるので、**これはコンソールが
被写体に重なり始めるまさにその瞬間**でした。1 を直したら
**肺の下葉がコンソールの下に潜りました**。いまは「帯に入り込んでいるか」で
判定します。rail は同じ扱いにしていません——スマートフォンでは上隅の
要約で、モデルはその後ろに無いからです

- 実画面（1280×800・`nose` `lung` `skin` `pancreas`）: 肺・皮膚・鼻は
  **明らかに大きくなり**、コンソールにも被りません。膵臓はほぼ変わりません
- 再発防止: `verify:anatomy` に手順 0 を足しました——
  **開いた直後と「表示をリセット」後で、モデルが画面を占める幅が変わらないこと**。
  モデルの上にカーソルを置いて左右の端を測るので、絵の比較ではありません。
  直す前のビルドでは鼻が `0.2..0.58` → `0.24..0.52` で落ちます

- **F-108 Trust ページの tab 巡回が閉じない** — 解決（2026-09-15）。
  **Trust ページの不具合ではなく、チェック側の欠陥でした。**
  `walkTabOrder` の歩数は `Math.min(controls + 8, MAX_TAB_STEPS)` で、
  `MAX_TAB_STEPS` が 240。Trust は出典リンクだけで 275 本、focusable 計 **295 個**
  あるので上限が毎回噛み、`if (stops >= steps) stuck = true` が
  **「focus is trapped or looping」と報告**していました。
  **232 個を超える操作を持つページは、tab 順が完璧でも必ずトラップと報告される**
  構造です。「46 本のリンクに tab が届かない」も同じ原因——歩き切る前に止まったので
  印が付いていないだけで、届かないわけではありませんでした。
  6 件すべてが同じ 1 つのバグです。

  直し方は上限を上げることではなく、**上限と診断を切り離すこと**でした。
  `walkTabOrder` は終わり方を `closed` / `left` / `cut` で返し、`cut`（予算切れ）は
  トラップと呼びません。予算は `controls * 2 + 8`（閉じる環は最初の stop への
  2 周目で閉じるため）、`MAX_TAB_STEPS` は無限ループを止めるためだけの天井として
  1200。そして **`cut` のときは印を読まない**——読めば、歩かなかった先の全部が
  「届かない」と出るからです。

  **抑制ではないことを確かめています**: `.trust-nav` に focus を閉じ込める
  focusin ハンドラを仕込んだ dist で同じチェックを走らせると、
  **exit 1・11 problems**（`feedback-trigger` 1 件＋リンク 280 件が「tab が届かない」）。
  健全な巨大ページは緑、本物のトラップは赤です。
  なお、このチェックが実際にトラップを見つける手段は歩数ではなく
  **unreachable の測定**の方で、そちらは触っていません。
  `verify:ui` は全 viewport × 全 surface で **0 problems**。

`urinary-obstruction` and `lobar-collapse` both claim something about **how
many** — one kidney or two, one lung or the other — so both draw the pair. At
phone width the info cards in the top-left overlap the left-hand member of the
pair at rest. Nothing is unreadable and no label fails the band check, so this
is not a defect being reported; it is a case the shell's layout has not had to
consider before.

### F-93 — "draw the space, not the displacement" has now happened four times

Hip, shoulder, urinary obstruction and lobar collapse each computed a
displacement that came out at single-digit pixels, and each solved it the same
way: draw the space the displacement opened, or draw a second marker at the
resting position so the reader sees a gap rather than remembering a location.
`docs/organ-3d-playbook.md` records the failure modes of *surfaces*; this is a
failure mode of *quantities*, and four instances is enough to write it down.

Not blocking anything — the scenes are correct. Offered as a playbook entry.

*Raised by Claude③.*

### F-94 — a scene that draws its own scale has to be framed for the narrowest screen

`pressure-injury` reports a profile against depth, and the only honest way to
draw a comparison between four depths is a bar per depth beside the subject.
That makes the scene about five units wide and four tall — and a portrait phone
shows far less across than down, so the longest bar (the answer) ran off the
right edge at the default pose while the desktop shot was fine.

The fix was to bound the bar length by what phone width can hold and to pull the
default pose back until both the block and its read-out fit. Nothing in the
tests could have caught it: the bars were at the coordinates the model gave.

Worth noting because **any scene that draws a read-out beside its subject rather
than on it** inherits this, and the constraint is not the subject's size but the
subject-plus-read-out's *aspect*. Related to F-89.

*Raised by Claude③ from `claude/pathology-expansion-b4`. For Claude① / Work.*

### F-95 — "it spread" is drawn by a picture before any model computes it

`breast-lesion` is the first scene in this repository whose subject a reader
arrives at with a narrative already fixed — starts small, grows, reaches the
nodes. Three separate drawing decisions had to be made *against* that narrative
rather than merely omitting it:

- the marker is **one fixed size** everywhere, because a marker that grew along
  the axis is a diameter whether or not anything computed one;
- the drainage route and the node group are held **byte-identical** across every
  position on every course, because a route that lit up would say something had
  travelled it;
- the distance is drawn as **beads rather than a cord**, because a solid line
  joining a place to a drainage route reads as a conduit.

A model test measures all three off the drawing rather than off the return
value. Recorded because the general rule — *for a subject with a received
narrative, the absences have to be drawn, not just left out* — will apply again
(any tumour subject, any infection spreading, any embolus).

*Raised by Claude③. Offered as a playbook entry, not blocking anything.*

### F-96 — six more pathology scenes are registered with no clinical review

`lumbar-disc-herniation`, `retinal-detachment`, `cataract`, `bppv`,
`pressure-injury` and `breast-lesion` are all `alpha` with
`docs/clinical-reviews/registry.json` at `reviewStatus: pending`. Each carries a
model profile, an evidence dossier, a model card, a scope panel and a patient
guide, and each names its own unresolved limitations in the registry.

Four of the six make a refusal their central claim — no symptom, no acuity, no
nystagmus, no stage, no spread — and those refusals are the part a clinical
reviewer most needs to check the wording of, because they are what a reader will
otherwise fill in. Same shape as F-40 and F-45.

### F-97 — the ledger's own `F-<n>` numbers are not unique

`F-44` through `F-47` each appear three times in this file and `F-87` through
`F-93` twice, written by different authors at different times. The ledger's
rules say a number is never reassigned so that a conversation or a PR can point
at one — which only works if a number names one item.

Not fixed here, deliberately: renumbering is exactly what the rule forbids, and
every duplicate is somebody else's entry. What would fix it is a convention for
the next number (a note at the top saying what has been used), or a check that
fails on a duplicate heading. Whoever owns this file should pick one.
