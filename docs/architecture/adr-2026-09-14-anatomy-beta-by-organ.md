# ADR 2026-09-14 — 解剖βは、通った臓器から 1 つずつ開く

Status: Accepted（実装済み）
所有: 公開範囲の判断。実装は [`../../src/catalog/release.js`](../../src/catalog/release.js)、
現在の状態は [`../beta-release.md`](../beta-release.md)。
[ADR 2026-09-08](adr-2026-09-08-anatomy-only-beta.md) を**置き換えません**——
その判断（解剖層だけを公開する、候補一覧は公開ではない、公開判断記録は医学レビューでは
ない、channel 名では公開しない）はすべて維持します。**変えるのは範囲の書き方 1 点**です。

## Context

2026-09-08 の ADR は「公開βは**脳と心臓の**解剖」と書きました。そのとき解剖シーンは
脳 1 つしか合格しておらず、心臓の解剖シーンは存在すらしていなかったので、
**範囲＝臓器の名前 2 つ**で書いても実質的な差はありませんでした。

現在、手続き生成の臓器解剖シーンは 37 あります。どれも
`betaPublicationProblems()` の 5 条件のうち 4 つを満たしていて、
落ちているのは 2 つだけです——候補一覧に名前が無いことと、公開判断記録が無いこと。
前者は「範囲」という判断で、後者は「誰かが実際に見たか」という作業です。

**この 2 つを混ぜると、範囲の判断が作業の進み具合で決まってしまいます。**
逆も同じで、範囲を臓器名で固定すると、合格した臓器を開くのに ADR の改訂が要ります。

## Decision

**βの範囲は「解剖層のうち、ゲートを通ったもの」です。臓器名では固定しません。**

1. `BETA_ANATOMY_CANDIDATES` は**開く意思のある**シーンの一覧で、公開ではありません。
   合格したものだけが開きます（5 条件は 2026-09-08 の ADR のまま）
2. **1 つずつ開きます。** 1 バッチ = 数シーンで、各シーンに公開判断記録が要ります。
   「37 件まとめて」はしません——記録は誰かが実際に見た証跡であって、
   数を揃えるための書式ではないからです
3. **「見る」は実レンダリングです。** B1（肺・肝・腎）でそれが実証されました：
   `npm run verify:anatomy` は 3 件とも通り、そのうえで全視点をレンダリングしたら
   欠陥が 3 つ出ました（F-44 framing・F-101 断面・F-102 dispose）。
   **ゲートが開くことは、見たことの代わりになりません**
4. **順番は [`../public-release-roadmap.md`](../public-release-roadmap.md) §1Z が持ちます。**
   ADR は順番を持ちません——順番は変わるからです
5. **A2 未満の臓器は開きません。** `skeleton-overview` と `lymphatic-drainage` は
   A1 なので、台帳（[`../../src/catalog/anatomy.js`](../../src/catalog/anatomy.js)）が
   A2 を記録するまで候補にしません
6. **病態層は変わらず非公開です。** 次期 β（`next-beta` policy）の話であって、
   このβの範囲ではありません

## Consequences

- 臓器が 1 つ増えるたびに ADR を書き直す必要はなくなります。増えるのは
  候補一覧の 1 行と、公開判断記録 1 通と、レンダーを見た事実です
- 「公開 1 件」を前提にしていた文言は事実側へ寄せます
  （`beta-release.md`、`tests/beta-release.test.js` の期待値、リンクカードの件数）
- hero のローテーションは公開集合で絞られるので、公開臓器が増えれば自動的に増えます
  （`src/data/landingHero.js` の `HERO_ORGANS` に載っているものだけ）
- **心臓は依然として開きません。** 候補 asset が asset release gate を通っておらず、
  公開判断記録もありません。名前が候補にあることは公開ではない、のままです
