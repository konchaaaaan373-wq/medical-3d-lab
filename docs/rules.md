# Rules — 運用ルール台帳

Last updated: 2026-11-24

開発の途中で決まった**ルール・こだわり・やり方の約束**を、日付つきで 1 か所に置く
台帳です。`CLAUDE.md` が規則の**要約**、本書がその**時系列の記録**で、
どちらを読んでも同じ結論に着くことが条件です。

この台帳は [`verification-lessons.md`](verification-lessons.md)（検証が嘘をついた事例）とも
[`follow-ups.md`](follow-ups.md)（未確認・未決定）とも違います。あそこに置くのは
**失敗**と**残課題**で、ここに置くのは**「こうする」と決めたこと**です。
設計判断の経緯が長くなるものは従来どおり `architecture/adr-*.md` に書き、
ここにはその ADR を指す 1 項目だけを置きます。

---

## 使い方 — 3 つの約束

1. **常に md を参照する。** 作業の前に読む順は
   `CLAUDE.md` → **本書の「現行」節** → [`grand-design.md`](grand-design.md) §1 の
   document map → 該当する所有文書。会話の記憶や前回のセッションの印象から
   ルールを思い出さないでください。書いてないルールは無いルールです
2. **ルールが生まれたら、同じ PR で本書に 1 項目足す。** セッション中に所有者が
   「以後こうして」「ここはこだわる」と言ったら、それは作業指示ではなくルールです。
   「あとで書く」は書かれません（[`verification-lessons.md`](verification-lessons.md) の
   実測: 0 件）。要約が要るなら `CLAUDE.md` にも同じ趣旨を 1 行足します
3. **古いルールは消さない。新しい日付が勝つ。** ルールを変えるときは、
   新しい項目を「現行」の先頭に足し、置き換えられた項目を「アーカイブ」へ**本文ごと**
   移して、どの項目が置き換えたかを書きます。矛盾する 2 つの項目があれば、
   **日付の新しいほうが優先**です（同じ日なら連番の大きいほう）。
   `CLAUDE.md` や所有文書の本文が本書の新しい項目と矛盾したら、**本書の新しい
   項目が勝ち**、見つけた人が本文を直します

`npm run rules`（`npm test` からも走ります）が台帳の形を守ります——各項目が
3 つの欄を持つこと、番号が重複しないこと、「現行」が新しい順に並んでいること、
置き換えられた項目が**消されずにアーカイブへ移っている**こと、
アーカイブの項目が**どの現行項目に置き換えられたか**を名指ししていること、
そして **一度この台帳に載った番号が 1 つも消えていないこと**
（[`tests/rules-ids-baseline.json`](../tests/rules-ids-baseline.json) が、載ったことのある番号を
全部持ちます。項目を足したら `npm run rules -- --write` で 1 行足します。この一覧は増えるだけで、
減らす書き込みは拒まれます——消えた番号を見つけるのがこの一覧の仕事だからです）。
ルールの中身が正しいかは機械では確かめられません。それは読む人の仕事です。

### 書き方

```markdown
### R-YYYY-MM-DD-NN — 1 行で「こうする」

- **決めたこと**: 命令形で。何をする・しない
- **なぜ**: どの失敗・どの要望から来たか。実例があれば日付つきで
- **置き換えるもの**: `R-YYYY-MM-DD-NN`（本文はアーカイブへ移す）／なし
```

番号は `R-<決めた日>-<その日の連番 2 桁>` で、再採番しません。
アーカイブへ移すときは、本文の末尾に 1 行足します。

```markdown
- **置き換えたもの**: `R-YYYY-MM-DD-NN`（アーカイブへ移した日: YYYY-MM-DD）
```

## 現行（新しい順）

### R-2026-11-24-04 — ピンクは製品の色で、領域の色ではない

- **決めたこと**: ブランドピンク（`#E879A6` 系）は、マーク・主要ボタンの矢印・現在地・選択だけに
  使う。解剖アトラスや MRI のラベルの配色にピンクの色相を使わない。細い線や文字として薄い地に
  置くときは深いピンク（マーク `#C94C80`、文字 `#A62F61`）を使い、`#E879A6` を文字色にしない。
  紙は `#FAF9FC`、インクは `#252633`、3D と MRI の地は `#171820`。トークンは既存の
  `--reading-*`・`--bg` を差し替えたもので、2 組目を作らない
- **なぜ**: 所有者の指示（2026-11-24）「ブランドカラーと解剖学的な領域色を混同させない」
  「WCAG AA 相当のコントラストを確保する」。`#E879A6` は `#FAF9FC` の上で 2.6:1 しかなく、
  文字にも細い線にも足りない。MRI 画面で領域色とブランド色が同じ色相だと、選択の強調と
  ラベルが見分けられなくなる。`tests/mri-atlas-data.test.js` が配色の色相を固定する
- **置き換えるもの**: なし（[ADR 2026-09-30](architecture/adr-2026-09-30-byoki-motion.md) の
  「オレンジは操作・選択・変化だけ」をピンクで引き継ぐ。ADR は台帳の項目ではないのでアーカイブ対象ではない）

### R-2026-11-24-03 — MRI と 3D の対応は「同じ座標」か「同じ名前」かを必ず言い分ける

- **決めたこと**: MRI に連動する 3D は、断面を塗っているのと同じラベルボリュームから作る
  （`scripts/build-mri-atlas.mjs`）。既存の `brain.glb` に MNI 座標を当てはめない。
  2 つのアトラスをつなぐのは、両方が 1 つの塊として同じ名前・同じ左右で描いている構造だけで
  （`ANATOMY_ATLAS_LINKS`）、画面に「名称による対応」と書く。左右は絵で確かめず数で確かめる
  ——ビルド・テスト・ブラウザ起動時の 3 か所で、ラベルの重心の x とアトラスの半球表を照合する。
  構造を選んだときの十字線は重心ではなく、ラベル内部の最深点へ送る
- **なぜ**: 所有者の指示（2026-11-24）「厳密な空間対応と、構造名に基づく概念的対応を混同しない」
  「左右反転、座標ずれ、ラベル不一致を検証する」。対称テンプレートでは鏡像の画面が正しい画面と
  同じに見えるので、目視は検証にならない。重心は 102 構造中 36 で構造の外に落ちる
  （実測。`verify:mri` を重心に変異させると側脳室の十字線が視床に載る）
- **置き換えるもの**: なし

### R-2026-11-24-02 — 「中心に置く」は「開ける」ではない。機能の主張は、閉じたモデルの外に書かない

- **決めたこと**: 公開ビルドで開いている面（トップ・`#/functions`・脳解剖・MRI アトラス）に、
  「どの構造がどの機能を担うか」を書かない。高次脳機能の学習テーマは**問い**として出す
  （`src/data/brainFunctionThemes.js`）。機能の主張は `higher-brain-function` のモデルと
  根拠資料が持ち、そのモデルが公開ゲートを通ったときにだけ画面に出る。閉じていることは、
  リンクを消したり灰色にしたりせず言葉で伝える。AI による文献確認を医学レビュー済みとして
  扱わない
- **なぜ**: 所有者の指示（2026-11-24）「公開ゲートを安易に解除せず」「AIによる文献確認を、
  人間の医学レビューが完了したものとして扱わない」と、同じ指示の「高次脳機能をサービスの
  中心に」を両立させるため。入口ページに構造名を並べれば、モデルを閉じたまま主張だけが
  公開される
- **置き換えるもの**: なし

### R-2026-11-24-01 — 初期ローンチの公開範囲は脳だけ。範囲は `LAUNCH_SCOPE` の 1 か所が持つ

- **決めたこと**: 公開するのは `organ: 'brain'` のシーンのうち、従来の公開ゲートを通ったものだけ。
  範囲は `src/catalog/release.js` の `LAUNCH_SCOPE` が持ち、ほかの場所に臓器名の一覧を書かない。
  範囲外のシーンは**消さない**——カタログ・公開判断記録・レビュー記録・テストを残し、
  `betaPublicationProblems` の答えも変えない。範囲を広げるのは `LAUNCH_SCOPE.organs` の編集で、
  所有者の判断。製品名は「3Dモデルラボ」（`src/data/brand.js`）、ヘッダーの行き先は
  `src/catalog/launch.js` の 3 つ（高次脳機能・脳解剖・MRIアトラス）
- **なぜ**: 所有者の指示（2026-11-24）「初期版では対象臓器を脳に限定」「他臓器や既存の病態モデルは
  削除せず、初期公開のナビゲーションや公開範囲から外す」「将来的に再公開できる拡張性を維持」。
  経緯と、何を上書きし何を維持したかは
  [ADR 2026-11-24](architecture/adr-2026-11-24-brain-launch.md)
- **置き換えるもの**: なし（製品名と「絵のロゴを持たない」は ADR 2026-09-30 の決定で、台帳の項目ではない。
  ADR 側に上書きの関係を書いた）

### R-2026-10-22-01 — Node の版は `.nvmrc` 1 か所が持ち、CI も Netlify もそこから読む

- **決めたこと**: Node の版は [`../.nvmrc`](../.nvmrc) の 1 行（LTS の偶数 major だけ。
  いまは `24`）。workflow の `actions/setup-node` は `node-version-file: .nvmrc` と
  `check-latest: true` で読み、版を literal で書かない。`netlify.toml` にも
  `NODE_VERSION` を書かない。Netlify の関数はビルドの Node で走るので、UI に
  `AWS_LAMBDA_JS_RUNTIME` を置かない（置くなら `.nvmrc` と同じ major）。
  版を変えるのは `.nvmrc` の 1 行で、写しは `tests/node-runtime.test.js` が拒む
- **なぜ**: 所有者の指示（2026-10-22）「Node 24 LTS へ移行し、CI と Netlify ビルドを
  整合」。それまで CI は 12 か所で `22` と書き、Netlify がビルドと関数
  （毎時の `scheduled-billing-reconcile` を含む）に使う版は repo のどこにも無く、
  CI の緑は出荷物の Node について何も言っていなかった
  （[`verification-lessons.md`](verification-lessons.md) L-182）。major だけを書くのは、
  2026-10-20 の 24.22.1 のような patch のセキュリティリリースを、CI と deploy が
  commit なしで同じ経路から受け取るため
- **置き換えるもの**: なし

### R-2026-10-16-02 — 古いルールは削除せずアーカイブし、新しい日付を優先する

- **決めたこと**: ルールを変えるときは、新しい項目を足して古い項目を「アーカイブ」節へ
  本文ごと移す。削除しない。矛盾する項目は日付の新しいほうが勝つ（同日なら連番の
  大きいほう）。アーカイブの項目は参照用で、現行の判断には使わない
- **なぜ**: 所有者の指示（2026-10-16）。「古いものは削除せずアーカイブして、日付が
  新しいものを重要度を高めて参照し続ける」。消すと**なぜ変えたか**が消え、同じ議論を
  繰り返す。この repo は ADR で同じことをしている（2026-09-08 の「解剖だけ」を
  2026-09-22 の ADR が上書きし、旧 ADR は残したまま「何を上書きし何を維持したか」を
  書いた）。本書はそれをルール単位で、軽い形で行う
- **置き換えるもの**: なし

### R-2026-10-16-01 — 運用ルールは md に書き、常に md を参照する

- **決めたこと**: 開発中にルール・こだわり・やり方の約束が生まれたら、**同じ PR で**
  本書「現行」節の先頭に 1 項目足す。作業の前には `CLAUDE.md` → 本書 →
  `grand-design.md` §1 → 所有文書の順に読み、記憶や印象からルールを思い出さない。
  本書より前に書かれた `CLAUDE.md` と `docs/` の本文は、本書の項目と矛盾しない限り
  そのまま有効（日付の無い本文は、どの日付つき項目よりも古いものとして扱う）
- **なぜ**: 所有者の指示（2026-10-16）。「今後の運用は常に md を参照する。
  ルールやこだわりが発生したら常にルール md を更新する」。これまでルールは
  `CLAUDE.md` の本文に散らばっていて、**いつ・なぜ決まったか**が追えなかった
  （例: 「hero に出せない臓器は公開しない」は本文中に「2026-09-16 決定」とだけある）。
  日付つきの台帳にすれば、後から来た項目が前の項目に勝つことを機械的に言える
- **置き換えるもの**: なし
