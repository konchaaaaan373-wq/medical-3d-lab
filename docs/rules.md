# Rules — 運用ルール台帳

Last updated: 2026-10-16

開発の途中で決まった**ルール・こだわり・やり方の約束**を、日付つきで 1 か所に置く
台帳です。`CLAUDE.md` が規則の**要約**、本書がその**時系列の記録**で、
どちらを読んでも同じ結論に着くことが条件です。

この台帳は [`verification-lessons.md`](verification-lessons.md)（検証が嘘をついた事例）とも
[`follow-ups.md`](follow-ups.md)（未確認・未決定）とも違います。あそこに置くのは
**失敗**と**残課題**で、ここに置くのは**「こうする」と決めたこと**です。
設計判断の経緯が長くなるものは従来どおり `architecture/adr-*.md` に書き、
ここにはその ADR を指す 1 項目だけを置きます。

---

## 使い方 — 3 つの約束

1. **常に md を参照する。** 作業の前に読む順は
   `CLAUDE.md` → **本書の「現行」節** → [`grand-design.md`](grand-design.md) §1 の
   document map → 該当する所有文書。会話の記憶や前回のセッションの印象から
   ルールを思い出さないでください。書いてないルールは無いルールです
2. **ルールが生まれたら、同じ PR で本書に 1 項目足す。** セッション中に所有者が
   「以後こうして」「ここはこだわる」と言ったら、それは作業指示ではなくルールです。
   「あとで書く」は書かれません（[`verification-lessons.md`](verification-lessons.md) の
   実測: 0 件）。要約が要るなら `CLAUDE.md` にも同じ趣旨を 1 行足します
3. **古いルールは消さない。新しい日付が勝つ。** ルールを変えるときは、
   新しい項目を「現行」の先頭に足し、置き換えられた項目を「アーカイブ」へ**本文ごと**
   移して、どの項目が置き換えたかを書きます。矛盾する 2 つの項目があれば、
   **日付の新しいほうが優先**です（同じ日なら連番の大きいほう）。
   `CLAUDE.md` や所有文書の本文が本書の新しい項目と矛盾したら、**本書の新しい
   項目が勝ち**、見つけた人が本文を直します

`npm run rules`（`npm test` からも走ります）が台帳の形を守ります——各項目が
3 つの欄を持つこと、番号が重複しないこと、「現行」が新しい順に並んでいること、
置き換えられた項目が**消されずにアーカイブへ移っている**こと、
アーカイブの項目が**どの現行項目に置き換えられたか**を名指ししていること。
ルールの中身が正しいかは機械では確かめられません。それは読む人の仕事です。

### 書き方

```markdown
### R-YYYY-MM-DD-NN — 1 行で「こうする」

- **決めたこと**: 命令形で。何をする・しない
- **なぜ**: どの失敗・どの要望から来たか。実例があれば日付つきで
- **置き換えるもの**: `R-YYYY-MM-DD-NN`（本文はアーカイブへ移す）／なし
```

番号は `R-<決めた日>-<その日の連番 2 桁>` で、再採番しません。
アーカイブへ移すときは、本文の末尾に 1 行足します。

```markdown
- **置き換えたもの**: `R-YYYY-MM-DD-NN`（アーカイブへ移した日: YYYY-MM-DD）
```

## 現行（新しい順）

### R-2026-10-16-02 — 古いルールは削除せずアーカイブし、新しい日付を優先する

- **決めたこと**: ルールを変えるときは、新しい項目を足して古い項目を「アーカイブ」節へ
  本文ごと移す。削除しない。矛盾する項目は日付の新しいほうが勝つ（同日なら連番の
  大きいほう）。アーカイブの項目は参照用で、現行の判断には使わない
- **なぜ**: 所有者の指示（2026-10-16）。「古いものは削除せずアーカイブして、日付が
  新しいものを重要度を高めて参照し続ける」。消すと**なぜ変えたか**が消え、同じ議論を
  繰り返す。この repo は ADR で同じことをしている（2026-09-08 の「解剖だけ」を
  2026-09-22 の ADR が上書きし、旧 ADR は残したまま「何を上書きし何を維持したか」を
  書いた）。本書はそれをルール単位で、軽い形で行う
- **置き換えるもの**: なし

### R-2026-10-16-01 — 運用ルールは md に書き、常に md を参照する

- **決めたこと**: 開発中にルール・こだわり・やり方の約束が生まれたら、**同じ PR で**
  本書「現行」節の先頭に 1 項目足す。作業の前には `CLAUDE.md` → 本書 →
  `grand-design.md` §1 → 所有文書の順に読み、記憶や印象からルールを思い出さない。
  本書より前に書かれた `CLAUDE.md` と `docs/` の本文は、本書の項目と矛盾しない限り
  そのまま有効（日付の無い本文は、どの日付つき項目よりも古いものとして扱う）
- **なぜ**: 所有者の指示（2026-10-16）。「今後の運用は常に md を参照する。
  ルールやこだわりが発生したら常にルール md を更新する」。これまでルールは
  `CLAUDE.md` の本文に散らばっていて、**いつ・なぜ決まったか**が追えなかった
  （例: 「hero に出せない臓器は公開しない」は本文中に「2026-09-16 決定」とだけある）。
  日付つきの台帳にすれば、後から来た項目が前の項目に勝つことを機械的に言える
- **置き換えるもの**: なし

## アーカイブ（置き換えられたもの。消さない）

まだありません。置き換えが起きたら、置き換えられた項目を本文ごとここへ移し、
末尾に **置き換えたもの** の 1 行を足します。
