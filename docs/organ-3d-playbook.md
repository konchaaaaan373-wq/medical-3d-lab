# 臓器 3D の実装知見

heart-failure シーンを「概念的な 3D」から「解剖図として通用する 3D」へ引き上げる
過程で見つかった、**臓器に依存しない**失敗モードと、その見つけ方をまとめた文書です。

設計上の規則は [`architecture-rules.md`](architecture-rules.md)。こちらは
**レンダリングの実務**、つまり「なぜ CG に見えるのか」「なぜ直したはずが直らないのか」
を扱います。新しい臓器を作るとき、以下はほぼ確実に同じ形で出てきます。

---

## 1. 推測せず測る

この文書で最も重要な節です。**4 回、原因を取り違えました。** そのいずれも、
もっともらしい仮説を立てて修正し、レンダリングして「変わっていない」を繰り返した末に、
機械的な切り分けで初めて正体が分かっています。

| 症状 | 最初に疑ったもの（外れ） | 実際の原因 |
|---|---|---|
| 心尖が櫛で梳いた髪に見える | 肉柱フィールド／テクスチャの内容 | **UV レイアウト**（極でのテクセル圧縮） |
| 基部の白飛び | bloom threshold、clearcoat、環境光 | **rim light**（ただし飽和のため半減しても無変化） |
| うっ血左房がラベンダー | 加算合成の圧フィールド | **左房自身のマテリアル**の暗色化ターゲット色 |
| 大動脈が明るすぎる | マテリアル基本色の比較で 2.6 倍 | 実描画では**わずかに暗い**（代理指標が誤り） |

### 手順

推測が 1 度外れたら、以下に切り替えてください。議論より速く終わります。

1. **オブジェクトを 1 つずつ隠す。** `?qa` フックからシーングラフに触れ、候補を
   1 つずつ `visible = false` にして同じ画素を測る。効いた 1 つが犯人です。
2. **ライトを 1 つずつ隠す。** 形状で決まらなければ照明です。
3. **マテリアルのチャンネルを 1 つずつ無効化する**（`map` / `bumpMap` /
   `roughnessMap` / `vertexColors` / `flatShading`）。
4. **パラメータをスイープして毎回フレームを読み返す。** 1 点だけ見ても
   飽和や非線形で判断を誤ります（下記）。
5. **画素で測る。** 目視は「最も明るいのはどれか」を間違えます。
   輝度ヒストグラムか、注目点の平均値を取ってください。

### 飽和は自分の修正を隠す

rim light を 1.15 → 0.62 に**半減させても見た目が変わりませんでした。**
ハイライトが飽和しており、どちらの値でも 255 に張り付いていたからです。
**正しい修正が、失敗した修正に見えます。** スイープして初めて分かりました。

| rim 強度 | シルエット全体の平均輝度 | 問題のスポット |
|---|---|---|
| 0.62 | 47.1 | 243 |
| 0.16 | 47.9 | 212 |

この表が示したのは「この光は存在意義であるシルエット分離にほぼ何も貢献しておらず、
白飛びのほぼすべてに貢献している」ということでした。1 点の観測では決して出ない結論です。

### 代理指標を疑う

「大動脈が心筋より明るすぎるか」をマテリアルの**基本色**で比べると 2.6 倍でした。
**実際に描かれた画素**を（ジオメトリから投影した点で）測ると、わずかに暗い。
テクスチャと照明が差を埋めています。代理指標のままなら、存在しない問題を
直しに行くところでした。**測るなら、見えているものを測ってください。**

## 2. 失敗モード集

### A. 収束する先端の UV 極 → 放射状の筋

**症状**: 心尖・肺尖・腎極など、面が 1 点に収束する場所で、テクスチャが
放射状の筋になる。「櫛で梳いた髪」に見える。

**原因**: `u` がどの高さでも同じ回数だけ巻いていると、円周がゼロに向かう場所で
テクセルが方位方向に大きく圧縮され、同じ倍率で放射方向に引き伸ばされます。
**テクスチャの内容ではなく、落ちる場所の問題**です。mottle も grain も
模様も等しく引き伸ばされるので、内容を変えても直りません。

**対処**: 巻き数を局所円周に応じて減衰させる。ラチェが開いた帯（切開などで
ループが断たれている）なら継ぎ目は生じません。

```js
const wrap = 3 * lerp(APEX_UV_WRAP, 1, smoothstep(0, 0.42, v));
uvs[idx] = (phi / (Math.PI * 2)) * wrap;
```

極そのものは、どんなレイアウトでも破綻します。テクスチャ側で最後の数 % を
フラットへフェードさせる残余ガードを併用してください。

### B. 両面シェルは 2a − a² で合成される

**症状**: 両面描画した膜・襟・被膜が、連続しているはずの隣接構造より明らかに明るい。

**原因**: 光線が 2 回通過するので、不透明度 `a` の層が 2 枚で `2a − a²` に合成されます。
`a = 0.88` なら実効 0.986 — 隣の単層 0.88 より約 20% 明るくなります。

**対処**: 単層見えから逆算する。

```js
material.opacity = 1 - Math.sqrt(1 - singleLayerOpacity);   // 0.88 -> 0.654
```

### C. 加算オーバーレイは面積で効く

**症状**: 血管に付けたときは適切だった加算フィールドが、大きな腔に付けると
腔を光らせてしまう。

**原因**: 加算合成は面積に比例して総光量が増えます。細い管と腔では 1 桁違います。

**対処**: 対象ごとに重みを持たせる（頂点属性が手軽）。ただし**先に原因を確かめること**
——この症状で私は加算フィールドを疑い、実際は腔自身のマテリアルでした。

### D. 暗色化のターゲット色は色相を間違えると明るくなる

**症状**: 「うっ血で暗くなる」はずの組織が、進行すると**明るく**なる。

**原因**: `mix(base, target, amount)` の `target` が別の色相だと、
チャンネルによっては上がります。青紫をターゲットにすると B が上がり、
全体の輝度も上がってラベンダーになりました（実測 (139,95,112) → (142,111,142)）。

**対処**: ターゲットは**同じ組織の暗い側**に置く。うっ血した静脈組織なら
青紫ではなく暗い赤紫です。進行の両端で輝度を測って、意図した向きか確認してください。

### E. キャップ・切断面はゼロへ「滑らかに」閉じる

**症状**: 切開面や蓋の終端に、黒いヘアラインとシルエットの段差が出る。

**原因**: 閾値以下でゼロにスナップしていると、その閾値の**上**に
「2 面がほぼ一致し、ほぼ真横を向いた薄片」の帯が残ります。

**対処**: 開き具合と同じ範囲で滑らかに閉じる。断面が消えるのは、
その奥に空間がない場所だけなので情報は失われません。

```js
const collapse = 1 - smoothstep(0, CUT_FACE_OPEN, openFraction(t));
if (collapse > 0.001) { /* inner を outer へ lerp */ }
```

**検証**: 切断面を隠した状態と表示した状態で、シルエットの下端プロファイルを
比較する。1px 以内に収まれば、切断面はシルエットを乱していません。

### F. 2 つのファンで作るキャップにはブリッジが要る

**症状**: 2 頭の先端（乳頭筋など）が、正面から見ると**透けている**。

**原因**: リムの各辺を「近い方の頂点」へ張ると、リムは覆われますが
キャップが 2 つのファンになり、その境界に何も張られません。

**対処**: 頂点の切り替わる方位でブリッジ三角形を追加。
**検証**: インデックス列を組み直し、頂点に接するすべての辺が
2 三角形に共有されることを確認（ラチェ継ぎ目の同一頂点は同一視する）。

### G. オーバーレイは対象の変形に追随させる

**症状**: 病態を示すシース／被膜が、対象から浮いて「セロファンを巻いた」ように見える。
あるいは逆に、対象の内部に埋まって見えなくなる。

**原因**: 対象が膨張・拡張するのに、オーバーレイが静的だと、
**膨張しきった状態を避けられるだけの余裕**を最初から持たせる必要があり、
安静時には大きすぎるシェルになります。

**対処**: オーバーレイにも同じ変形を適用し、静的クリアランスを最小にする。

```js
// vertex shader
vec4 mv = modelViewMatrix * vec4(position + normalize(normal) * uEngorge, 1.0);
```

対象がスケールで変形するなら、オーバーレイも**同じスケール値**を読む
（別の入力から導出しないこと——Story の reveal と生理の congestion は別物です）。

### H. シルエット — テーパーは容積と戦う、傾斜は無料

**症状**: 遠景で臓器が「バケツ」「カプセル」に見える。側面がほぼ平行。

**試して失敗すること**: 「基部を太く、先端を細く」テーパーさせる。
半径がモデルの解いた容積で決まっている場合、**シルエットが変わる大きさの
テーパーは容積を壊し、容積を保てる大きさのテーパーは何も変えません**
（実測：前者で内腔が解かれた面から 21% 逸脱、後者でシルエットが 2px 移動）。

**効くこと**: **傾斜（せん断）**。せん断は容積を厳密に保存します。そして臓器を
幾何学的な原始形状と区別しているのは、細くなり方ではなく**軸が垂直でないこと**です。

心尖の側方偏位を 0.13 → 0.22 にしただけで、正面シルエットの下側輪郭は
同じ範囲で 30px → 114px 動きました。

**測り方**: 一定の高さ刻みで左右端の x を取り、高さあたりの移動量を出す。
「バケツ」は数字になります。

### I. 壁から生える構造は、根を splay して壁に埋める

**症状**: 乳頭筋・心耳・乳頭など、壁から立ち上がる構造が「貼り付けた円錐」に見える。

**原因（3 つ重なる）**:
1. 根がきれいな楕円の足で面の**上に**載っている
2. 軸が滑らか（旋盤で挽いた形）
3. 先端が 1 つの滑らかなドーム

**対処**:
1. 根を数本の筋束に分岐させ、束の**間で取り付け面より下に沈める**
2. 縦方向の浅い溝（線維束）
3. 先端を複数の頂に

さらに、**根は面の「上」ではなく「中」に着座**させます。構造は生えている面から
傾いて立つので、面のちょうど上に置くと反対側の側面が浮き、リムが平らな終端として
見えます。分岐を入れても残る症状です。

**やりすぎの兆候**: 分岐が「ヒレ」に見えたら強すぎます。円錐とは別種の誤答です。

### J. 壁厚は大きな 2 半径の差 — 不一致が増幅される

**症状**: 内外面それぞれに「容積保存」の正規化をかけたら、描画された壁厚が 25% ずれた。

**原因**: 厚さは 2 つの大きな値の**小さな差**です。小数第 3 位で違う定数を
それぞれに掛けると、差では大きな相対誤差になります。

**対処**: 対になる面には**同一の係数**を掛ける。そして係数のキーは
「メッシュが何で対を作っているか」に合わせる——**インデックスで対を作っているなら
インデックスで**。高さでキーする方が原理的に見えて、対になる行は高さが違うので、
それが対を壊す唯一の選択でした。

### K. 表面に載せた構造は、載せた表面が動いたら載せ直す

**症状**: 拍動する臓器の上を走る血管が、収縮期に表面から浮き上がる。
先端ほどひどく、シルエットの外に出て「空中に浮いた管」になる。

**原因**: 血管を **1 回だけ**、拡張末期の表面の上に置いた。
壁はフレームごとに動き、血管は動かない。
**そして、クリアランスのテストは全部「置いた瞬間」を測っていた**ので、
どのテストも気づきません。

**対処**: 表面を渡して構造を作る（構造側に表面の第 2 の意見を持たせない）だけでは
足りません。**表面が動くたびに置き直す** API を組み側に用意します。
局所的に動きが違う場合（虚血で動かない壁など）は、その局所量も一緒に渡し、
構造が「自分の下の壁と同じだけ」動くようにします。

```js
coronaries.layOn(beatingShape, { displace: (point, where) => { /* 局所の hold-back */ } });
```

**測り方**: 拡張末期と収縮中期の両方で、構造の各サンプルから
**実際に描かれているメッシュ**までの距離を測り、**比較**します。
絶対値は行間隔ぶん過大に出るので、比が要点です
（心筋虚血シーンでは 0.34 → 0.64、修正後 0.34 → 0.32）。

### L. 切断面のために書いた整形項を、切っていない面に適用しない

**症状**: 閉じているはずの回転体の縫い目が開き、背景が透けて見える。
中腹がいちばん広く、先端では閉じる。

**原因**: 切断縁を平面ではなく S 字に膨らませる整形項が、
**切断縁を楔から遠ざける向き**に効いていた。楔角 0 で同じ項を掛けると、
最初と最後の列が押し離されて隙間になります。
先端で閉じるのは、そこでは別の減衰項が既に効いているからで、
「先端のシールの問題」に見えるのが厄介なところです。

**対処**: 整形項の大きさを、**それが整形している構造そのもの**で頭打ちにします。
切断縁の膨らみは楔の中でだけ許され、楔を突き抜けてはいけない
——`min(1, cutAngle / maxBow)`。楔がなければ膨らみもありません。
既存シーン（99° の楔 vs 0.25 rad の膨らみ）ではこの係数は厳密に 1 で、
形は 1 ビットも変わりません。

**関連**: 縫い目の法線を溶接する条件も「楔がどこまで閉じたか」ではなく
**2 列が実際にどれだけ離れているか**で書きます。
前者は切った回転体では同じ行を選びますが、閉じた回転体では
先端付近しか溶接せず、前壁の全長に折り目が残ります。

### M. 曲面上の「地図」は、塗りでは描けない——境界線で描く

**症状**: 領域ごとに色を塗った臓器で、凡例には 3 色あるのに、実際の画面では
どこが境目か分からない。色を強くすると今度は「陶器の壺」になる。

**原因**: **照明が灰色でない**からです。ライトに色味があると、面の向きが変わる
だけで色度がずれます。心筋虚血シーンで測ると、**全頂点を 1 色に塗っても**可視面の
色度は **0.0447** 散りました。淡い着色 1 つ分と同じ大きさです。
つまり塗りの信号は、最初から同程度のノイズの上に乗っています。

さらに悪いことに、既定カメラから見える面のほとんどが 1 領域ということが普通に
起きます（このシーンでは可視頂点の 73% が左前下行枝の支配域）。
**回さない読者には、3 つの地図ではなく 1 つの領域しか見えません。**

**対処**: **境界を線で描く。** 線は局所コントラストなので、照明にも
カメラにも依存しません。

**測り方**: まず床を測ります——全頂点を同じ色にしてレンダリングし、
可視面の色度のばらつきを出す。領域ペアの分離がこの床を超えていなければ、
その塗りは地図になっていません。

**線は頂点色ではなくフラグメントシェーダで。** メッシュが 48 列なら
境界 1 頂点ぶんは画面上 25px の帯であって線ではありません。
線を頂点で描けるまでメッシュを細かくすると、毎フレームのコストが 4 倍になります。
`onBeforeCompile` で重みを attribute として渡し、`fwidth` で閾値をスケールすれば、
**どこでも・どの距離でも同じ数ピクセル**の線になります。

```js
// 上位2つの重みが並ぶところが分水嶺
float gap = topWeight - runnerUp;
float onLine = 1.0 - smoothstep(0.0, max(fwidth(gap) * widthPx, 1e-5), gap);
diffuseColor.rgb *= mix(1.0, darken, onLine);
```

**シェーダ注入の失敗は静かです。** `#include <color_fragment>` の名前が
将来の three.js で変われば、置換は何にもマッチせず、マテリアルは正常にコンパイルされ、
線だけが消えます。`THREE.ShaderLib` の実ソースに対してフックを走らせ、
注入が効いたことをテストで確かめてください。順序（塗りの**後**か）を見るときは
include を展開してから、しかも `lastIndexOf` で——最初の一致で見ると、
塗りが 2 回適用されて線が塗り潰される変異を見逃します。

### M2. 主張が「内側にある構造」のとき、深度順序は主張の一部

**症状**: モデルは正しく、テストは緑で、**主張している場所に読者は何も見ません。**
高次脳機能シーンは「弓状束を切ると復唱だけが落ちる」と言いながら、その弓状束は
皮質の下にあって**画面上に存在しませんでした**。15 秒の動画は「何も無いところで
信号が止まる」絵を流していました。同じ形で 3 回踏んでいます。

1. **皮質を薄くするだけでは深部は出てきません。** 読者は手前の皮質と奥の皮質の
   **2 層**を通して見るので、各層 0.26 なら透過は約 0.55 倍——尾状核は「にじみ」
   として届きます（§B の 2a − a² と同じ話で、ここでは減衰側）。0.14 に下げても
   絵はほとんど変わりませんでした。**透過率の調整では解けません。**
2. **解けたのは深度順序でした。** 経路が通る構造だけを `depthTest = false` で
   手前に描きます（**位置も大きさも変えません**——変えているのは描く順序だけ）。
   経路線が既にそうしているので、新しい約束ではありません。
3. **手前に出す対象を間違えると、大きい方が小さい方を塗り潰します。** 最初は
   経路上の皮質ノードも一緒に持ち上げ、側面視で**中前頭回が尾状核を完全に覆い
   ました**（両者は画面上でほぼ同じ場所を占めます）。持ち上げるのは
   **隠れている側だけ**です。
4. **「隠れているか」を素材のカテゴリで判定すると外れます。** 「線維束なら
   持ち上げる」とした結果、**脳梁と脳弓は対象外**になりました——アトラスはこの
   2 つを `tracts` ではなく `white_matter` に分類しているからです。脳梁離断の
   シーンは、また「見えない切断」に戻っていました。**隠れているかは位置の問題**で、
   素材の分類名とは別の軸です。
5. **例外を 1 つだけ明示する。** 終脳白質は「名前のついた束が無いときの置き場」
   なので、これを手前に出すと**脳全体が不透明な塊で覆われます**。持ち上げ規則から
   名指しで除外してあります。

**チェック**: 新しいシーンで「この構造がこうなる」と言うたびに、**その構造が
既定カメラで実際に画素として見えているか**を 1 枚の絵で確かめてください。
`tests/higher-brain-function-model.test.js` の 2 件（経路の構造が手前に出ること・
終脳白質は決して出ないこと）が退行を捕まえます。ミューテーション 2 件で赤を確認。

### M3. 「どこで止まったか」を、止まった位置の小さなマーカーで語らない

**症状**: M2 で線維束を見えるようにしたあと、高次脳機能の 15 秒動画は
「失語の名前は**どこで止まったか**」を主張として掲げ、前・後・あいだの 3 か所で
切った絵を並べました。**病変の赤は見分けられ、止まった場所は見分けられません
でした。** 止まった場所を語っていたのは、経路線の上に止まる**半径 0.13 の球**で、
**経路線と同じ色**です。675px 幅の 9:16 フレームでは数ピクセルで、前で止まった
絵と後ろで止まった絵が**同じ絵に見えます**。

**原因の一般形**: **量を「点の位置」で符号化すると、点の大きさの分しか読めません。**
「どこまで届いたか」は経路**全体**の性質なので、経路全体が語れます。

**解**: 経路のチューブに頂点色を持たせ、**届いたところまでを明色、その先を中立の
暗色**にしました（`_paintRouteReach`）。前病変では線のほぼ全長が明るく、後病変では
後方の一部だけが明るい——**2 枚を並べれば一目で違います**。位置も大きさも解剖も
動かしていません。動かしたのは色だけです（CLAUDE.md の
"Never alter physiology for visual impact" の許す範囲）。

**やってはいけないこと**: 届かなかった側を**病変色**で塗ること。そこは無傷で、
単に到達しなかっただけです。病変色で塗れば「経路全体が壊れている」という**別の、
そして誤った主張**になります。マーカー自身の色規則が既に同じ間違いを 1 度
してあり（「通過中ずっと暗くしていた」）、その教訓がここにも効きます。

**チェック**: 「差」を主張する絵は、**その差が出る 2 枚を実際に並べて見る**。
状態のテストは 2 枚が違うことを言えますが、**見分けられることは言えません。**
`tests/higher-brain-function-model.test.js` の
`scene: the route is lit as far as the word got, and neutral past it` が、
明色部分の長さが 2 つの病変で**線の 1/10 以上**違うことまで固定します
（ミューテーション 4 件で赤を確認）。

### N. デフォルトカメラと Story カメラの向きは 1 か所から

**症状**: Story に入る／出る瞬間にカメラが大きく振れる。

**原因**: 「シーンが開く向き」と「Story の既定の向き」が別々の定数で、
片方だけを更新した。コメントには「両者は一致する」と書いてあった。

**対処**: 一致が要件なら、定数を 1 つにするか、テストで一致を固定してください。

### O. シルエットは裏返しでも同じ——巻き方向は測らないと分からない

**症状**: 血管が「丸い管」ではなく「平たいリボン」に見える。ハイライトが乗らない。
管の端が黒い穴になり、背景が透けて見える。

**原因**: 三角形の巻き方向が内向きだった。`TubeSurface` は
`indices.push(a, b, a + 1, ...)` と書かれており、**製品内の 42 本すべての管**と
大動脈基部が内側を向いていました。前面のみのマテリアルでは手前の壁が
カリングされ、**奥の壁**が描かれます。その法線はカメラ側を向くので、
陰影は「丸み」を失い、深度は管 1 本ぶん奥にずれます。
加えて `TubeSurface` は端に蓋が無く、開いた管でした。

**なぜ見逃されたか**: **管のシルエットは裏返しでも同じです。**
目視レビューでは通ります。1599 件のテストも通っていました。

**対処**: 2 つを測る。**閉じているか**（辺が正確に 2 面に共有されているか）と、
**外を向いているか**（符号付き体積が正）。
[`tests/mesh-quality.js`](../tests/mesh-quality.js) がその 2 つを測り、
`tests/organ-anatomy.test.js` が全臓器ぶん固定しています。

**併発する罠**: 巻き方向を直すと、**管の中身が隠れます**。
循環シーンの血流粒子とネフロンの濾液は、「手前の壁がカリングされていたから」
見えていました。壁を透過させるのが正しい表現ですが、
`tissueMaterial({ opacity: 1 })` は `transparent: false` かつ
`depthWrite: true` を作るので、**あとから `material.opacity` を書いても効きません**
（ネフロンの「濾液量を壁の不透明度で示す」制御は、これでずっと死んでいました）。
透過させる壁は、**生成時に**そう宣言してください。

**開いていてよい面もあります**: 弧（`arc < 2π`）の管、半ラーテの子宮・骨、
心室の切断面は、開いているのが目的です。だから
`OPEN_BY_DESIGN` に**理由つきで**列挙し、テストはその集合と**完全一致**を見ます
——閉じたのに残っている行も落とします。

### P. カテゴリ配色は、色相をメンバーの区別に使うとグループが消える

**症状**: 脳アトラスの 147 構造は**どの 2 つも見分けられていた**——全ペアの
CIE Lab 距離が ΔE ≥ 3.8 であることをテストが固定していました。それでも
スクリーンショットを見た人の第一声は「色の統一感がない」でした。
**前頭葉がどこで終わって頭頂葉がどこから始まるのかが、画面上で言えません。**

**原因**: 色相を**メンバーの区別**に使っていました。1 family に HSL で 75–130°（葉は 75–90°）、
実レンダリングの Lab 色相では前頭葉だけで **155°** の幅があり、同じ葉の中に
マゼンタから黄色までが並びます。前頭葉と頭頂葉の帯は互いに重なってもいました。
12 の family はどれも 61° 以上に広がっていて、**どれ 1 つとしてグループに
見えていません**。

**どう見つかったか**: 人が絵を見て言いました。**テストは緑のままです**——
「隣同士が見分けられるか」は測っていましたが、
**「同じ大分類が 1 つに見えるか」は誰も測っていませんでした**。
分離の指標は、それだけでは配色の品質ではありません。

**対処**: 2 つの軸を分ける。

- **グループの同一性は色相が持つ。** 大分類（葉・脳室系・小脳・脳幹）ごとに
  狭い色相帯を 1 本だけ与える。いまは Lab 色相で最大 34°
- **メンバーの区別は明度と彩度が持つ。** 帯の中で明度・彩度を振る
- **色相帯を狭めると、メンバー間の距離は縮む。** 実測で前頭葉の最近傍 ΔE 中央値は
  10.9 → 6.4 に落ちました。明度・彩度の箱を広げて取り返します（同 7.3）。
  **この取引は避けられないので、両方を測ってから決めてください**
- **配置がハッシュなら、family ごとに seed を振って探索する。** 35 個の深部核に
  十分に均す seed は、21 個の前頭回には十分ではありません。1 本の seed で
  全アトラスを賄うと、いちばん混んでいる family が全体の下限を決めます
- **legend の色は帯の中心から導く。** 手で選んだ hex を別に置くと、帯を動かした
  日に legend だけが前の配色を約束し続けます

**そして、色相だけでグループを持たせた配色は、次の読者で崩れます。**
指摘を受けて測ったら、**シミュレーション下で葉が消えていました**——2 型
（deuteranopia）で側頭葉と後頭葉が **ΔE 0.5**、前頭葉と頭頂葉が **3.0**。
正常色覚では 27 と 23 あります。**帯を分けていた軸が、その読者には無い軸でした。**
しかも**その前の配色も同じくらい壊れていて**（0.5 / 2.8）、
**グループ化の改善はこの問題を直しも悪化もさせていません**——別の軸の話だからです。

**ここで一度やりすぎました。** 色覚側を目的関数にして解いたら 4 視すべてで
ΔE 12 以上まで上がりましたが、**中心溝（前頭葉↔頭頂葉）が 18.7 まで落ち**、
人が見て「頭頂葉の境目がわかりづらい」と言いました。**全 family の全組み合わせの
最小値を最大化していたので、同時に見えない組にも予算が流れていた**のが原因です
（[L-72](verification-lessons.md)）。目的関数と制約を入れ替えて解き直し、
**接している組だけ**に床を置いたら両方良くなりました。

**「では赤と緑は使えないのか」——使えます。** 禁じられているのは
**「区別が要る 2 つを赤–緑の差**だけ**に頼らせること」**であって、色相そのものでは
ありません。実際に赤（辺縁葉）と緑（頭頂葉）を入れ、接する相手との間に**明度差**を
併せて持たせたところ、通常色覚の中心溝は実レンダ実測で **49.4**（それまでの最良が
31.9）、2 型でも **32.9** と、**両方とも最良**になりました。
**彩度を下げることも必須ではありません**——それは私が安全側に振りすぎた判断でした。

**ただし赤を足すと色覚側の下限は下がります（実測 4.7 → 3.8）。**
P/D 型に残る色度軸は 1 本で、**赤・橙・茶はその同じ側に載る**ので、
互いを離す手段が明度しか残らないためです。**この費用は測ってから払うこと。**

**対処**: どちらが目的でどちらが制約かを先に決め、残る 2 つの信号を使う。

- **通常色覚の「接している境目」を目的関数にする。** 読者がたどるのは中心溝や
  小脳の縁であって、前頭葉と後頭葉の距離ではありません。接する組は**解剖であって
  メッシュ名から導けない**ので、列挙してテストに持たせます
- **色覚配慮は「ただで買える分」を制約として取る。** 色相は赤–緑ではなく青–黄へ
  わずかに寄せ、隣り合う大分類に明度差を与える（側頭葉＝中間の紫／後頭葉＝
  明るい青）。これで最悪の組が ΔE 0.5 → 約 5 になります。
  **5 は「違う」であって「読みやすい」ではありません**——部分的な措置だと
  そのまま書くこと
- **中心を HSL 上で手設計しない。** 実際にやって外しました: 側頭葉 L72 /
  後頭葉 L44 と 2 段に分けたのに protan で ΔE 0.7 です。**P 型では紫が輝度を
  大きく落として青に寄る**ので、HSL の明度差は保存されません。
  **シミュレーション空間で解くこと**
- **どこまでを約束するか決めて、それだけ約束する。** 約束は**大分類どうし**だけ。
  1 つの family の中（葉の中の個々の回）は 2 色覚では分離しません。選択すれば
  名前が出る・一覧と層スライダーは色を使わない、で担保しています
- **シミュレーションは「崩れている」ことは言えても「崩れていない」ことの証明ではない**

**いま何が捕まえるか**: `tests/brain-anatomy.test.js` の 2 本です。
`each large anatomical unit reads as one colour family` が
各 family の Lab 色相スプレッド（legend swatch 込み）を 44° 以内に、
`the units that touch are told apart, and dichromacy gets what is free` が
**接する 18 組**の通常色覚での最小 ΔE に床 22 を、**表面に出る 8 family** の
protan / deutan / tritan での最小 ΔE に床 4 を置きます
（実測: 接する組の最小 31.4、色覚側 5.2 / 4.3 / 5.4）。
ミューテーション 3 件で赤を確認済み——1 件は**報告された不具合そのもの**
（頭頂葉を前頭葉の色調へ戻す → ΔE 8.5 で赤）、1 件は**色覚のアサーションだけ**を
落とします（脳幹を前頭葉の明度へ上げる → protan で辺縁葉と ΔE 0.6）。
全ペア ΔE ≥ 3.8 の監査も残してあり 4.31 → 4.17 です。**3 つは別々の主張なので、
どれかをどれかで置き換えないでください。**

**ミューテーションは当てたことを確かめてから緑を読むこと。** この節を書く途中で、
文字列置換が 1 文字違いで**黙って空振り**し、無改変のファイルを測って
「ガードが効かない」と結論しかけました（[L-71](verification-lessons.md)）。
`python3 scripts/mutate-colour-family.py <family> <field> <value>` が
置換後が異なることを assert してから書きます。

実レンダでの確認は `npm run shots:anatomy -- --cvd all`（または
`--cvd deutan`）が同じフレームの 2 色覚版を並べて書き出します。**スウォッチで
通っても、光の当たった面では別の話になり得ます**——実測（左側面、葉の中央を
平均）では中心溝が 26.3 → 22.9 → 31.9 → 49.4 → 50.0 → 72.7 → **79.0**、
2 型で 9.6 → 19.2 → 20.5 → 32.9 → 29.7 → 28.6 → **25.1**、P 型で **21.8** です。
**いちばん彩度の高い版がいちばん読みやすい**——「配慮＝彩度を落とす」ではありません。

### Q. カテゴリ配色を HSL で設計すると、彩度が揃わない

**症状**: 色相も境目も測って通したのに、**「カラーの存在感がない」「寄せ集めに見える」**と
言われました。測ったら理由は色相ではなく**彩度**です——HSL 上では
`saturation` を 52〜80 の範囲に収めていたのに、**知覚的な彩度（CIE の C*）は
39〜101 と 2.6 倍ばらついていました**（側頭葉の紫が 101 でほぼ色域外、
島皮質が 39）。**HSL の "saturation" は colourfulness ではなく、
"lightness" は brightness ではありません。**

**対処**: 設計を **CIE LCh** で行う。`lightness` は L*、`chroma` は colourfulness、
`hue` は Lab の角度で、等しい差が等しく見えます。

- **段ごとに彩度を 1 つ決める。** 皮質葉は全部 C62、補助は 48 / 40 / 36、
  中立は 26 / 14 / 9。**これが「一つの系に見える」ことの実体**です。
  ただし**色域の上限は色相ごとに違います**——青緑は C36 止まりで、赤の C62 には
  届きません。ガードは「揃っているか」ではなく
  **「その段の彩度か、その色相・明度で出せる上限か、低いほう」**を要求します
  （前者は配色ではなくディスプレイへの要求になってしまう）
- **色域から出たら彩度だけを引く。** `lchToHex` は L と h を保ったまま C を
  二分探索で詰めます。チャンネルを clip すると**色相が動いて**、
  1 つの葉だけ色が違って見える——差分では見えず画面では見えるずれです
- **明度のリズムは設計者が決める。** 接する境目ごとに明暗が入れ替わるように
  置く（赤 55 / 緑 74 / 菫 44 / 青 64）。探索に最大化させると**色域の端まで
  振り切って**、淡すぎる葉とネオンが混ざります
- **赤と緑が隣り合う境目は、明度で持たせる。** 前頭葉を赤にすると中心溝が
  **赤×緑**——2 色覚が色相ではまったく分離できない唯一の組になります。
  L* 50 対 61 の段差で持たせており、実レンダの中心溝は通常色覚で ΔE 79.0
  （色覚配慮前の最良 50.0）、P 型で 21.8 です。
  **「その色相を避ける」ではなく「別の軸を用意する」**が正解です
- **その明度差が、色をどこまで濃くできるかの上限を決めます。** 「頭頂葉を
  もっと緑に」は明度を下げることで、**下げたぶんだけ中心溝の段差が減ります**。
  掃引して測ると L* 61 が限界で、58 では P 型で ΔE 3.5、52 では 1.1 まで落ちます
  （床は 3）。**好みで決めず、崩れる点を測ってから決めること**
- **暖色は 3 つ置けません。** 赤の前頭葉の隣に琥珀と茶を並べると、
  P/D 型に残る 1 本の色度軸に 3 family が載り、明度だけで離すことになります。
  辺縁葉を青緑へ移して解きました
- **探索は「制約を満たすため」に使い、「美しさを最大化するため」に使わない。**
  目的関数を分離の最大化にした版は、明度が極端になって設計が壊れました

**いま何が捕まえるか**: `tests/brain-anatomy.test.js` の
`the colour map reads as one set, not twelve separate choices`
（各皮質葉が「段の彩度」か「色域上限」の低いほうに達していること）と、
`an unreachable chroma comes back as the most the display can give, at the same hue`
（届かない C を要求したとき、**色相が 2° 以上動かない・明度が 1.5 以上動かない**）。
側頭葉の chroma を 62→38 に落とすミューテーションで赤（開き 24）を確認済み。
色域処理を clip に戻すミューテーションでも赤になります。

**通常解剖色モードは HSL のままです。** あちらは手で選んだ組織色の狭い帯で、
カテゴリ配色ではないからです。**1 つのモジュールに 2 つの色空間があるのは、
2 つの別々の仕事があるからだ**と冒頭に書いてあります。

## 2.5. 臓器を「名前のついた部分」に切る

肺を「1 枚の面に溝を彫ったもの」から「5 つの閉じた葉」に作り替えたときの知見です。
**溝は葉ではありません。** 溝では隠せず、色を変えられず、体積を訊けません。
仕組みは [`shared/geometry/carve.js`](../src/scenes/shared/geometry/carve.js)。

### 前提: ワープした球は星型である

球を変位させて作った臓器は、内部のある点について**星型**です
（どの方向にも面をちょうど 1 回だけ横切る）。肺・肝・腎で成立を実測しました。
星型の立体と半空間の共通部分はやはり星型なので、
**「葉 = 臓器 ∩ 半空間」を方向ごとに `min(面までの距離, 平面までの距離)` で作れます。**
CSG ライブラリは要りません。成立しているかは `starShaped()` が答えます——
コメントで主張せず、測ってください。

### A. 異方性フレームでは、法線は点と同じ変換をしない

**症状**: 解剖学的な向き（「上前方 45°」）で書いた葉間裂が、肺の中では別の角度で
現れる。葉が互いに食い込み、**5 葉の体積合計が肺の 214%** になりました。

**原因**: 肺は幅の 2 倍の高さがあり、解剖フレーム → 局所座標は**異方スケーリング**です。
その下で平面の法線は点と同じようには変換されません（逆転置で変換されます）。

**対処**: 点は半径を**掛け**、法線は半径で**割る**。

```js
toLocal([lat, vert, ant])       { return set(lat*sign*half.x, vert*half.y, ant*half.z); }
toLocalNormal([lat, vert, ant]) { return set(lat*sign/half.x, vert/half.y, ant/half.z).normalize(); }
```

### B. 中心が自分の部分の外にあると、小さい部分ではなく別の立体ができる

**症状**: 右中葉が本来の 4 倍の体積で出てくる。

**原因**: 切り出しは「その部分の中心について星型」に作ります。中心が自分の領域の
外にあると、光線が最初に当たる平面が違い、まったく別の形が生成されます。

**対処**: 中心を**書かない**。領域内をサンプリングして重心を求める（`partCentroid`）。
裂の位置を動かしても中心が自動で追随し、書き間違えようがありません。

### C. 不動点反復は「中心が近いとき」だけ収束する

**症状**: 上葉が実体積の 2 倍。1 平面での単純な切断では正確なのに、葉では壊れる。

**原因**: 面までの距離を「半径の 2 次方程式を 3 回解く」不動点反復で求めていました。
距離場の原点と光線の原点が近ければ収束し、**離れると静かに収束しません**。
葉の中心はまさに離れています。

**対処**: 二分探索にする。f(t) =「面からどれだけ外か」は内側で負・外側で正なので、
ブラケットさえ張れば必ず正しい根に収束します。テーブル参照が数回増えるだけです。

### D. 切断面のリムはテッセレーション間隔でジグザグする

**症状**: 葉間裂の縁が階段状になる。

**原因**: 各頂点が独立に `min(面, 平面)` を取るため、平面が頂点方向の**間**を通ると、
「面を取った頂点」と「平面を取った頂点」が交互に並びます。

**対処**: 分割数を上げる。ここでは臓器 1 個のビルド費用が
**面のサンプリングに支配されていて切り出しではない**ため、detail 6 → 12 で
235 ms → 351 ms にしかならず、リムは目に見えて滑らかになりました。
**上げる前に、何が費用を占めているか測ってください。**

### E. 距離場の格子は、サンプルする面に合わせる

参照面が 1000 頂点しかないのに 128×256 の格子に散布すると、大半のセルが
補間で埋まり、**心切痕や肺門が丸められて消えます**（平均誤差 4%・最大 14%）。
散布をバイリニア（読み出しの随伴）にし、面を 24000 点で直接サンプルしたところ、
**平均 0.09%・最大 3%** になりました。溶接（`mergeVertices`）は距離場には不要で、
それが生成費用の大半でした——100k 頂点の溶接だけで 116 ms。

### F. 外接箱の割合は、臓器の表面ではなく楕円体の上の点

**臓器に入る構造の位置を「全長の何割」で書くと、その点は表面に乗りません。**
乗るのは外接箱の楕円体で、臓器はそれではありません。肺の肺門は
`[-0.86, 0.18, -0.14]` と、RALS の並びを半径の割合で書いてありました。実測すると
**8 つの肺門構造のうち 7 つが胸膜の外**、18 の区域中心のうち 3 つ（尖・後方——
肺が細くなるところ）も外で、気道と血管の端点 21 箇所が肺の外に出ていました。
実描画では血管が肺を突き破って空中で終わっているのが**一目で分かります**。
`npm test` は全部通っていました。どのテストも「表面はどこか」を訊いていなかったからです。

宣言は**方向**だけを与え、**距離は距離場が**与える、と分けます
（`radialSurface` / `radialClamp`）。この形にすると、外形のワープを変えても
肺門は表面に乗ったままです。

失敗モード I（壁から生える構造の根）の、**根の側が最初から壁の外にある**版です。

### G. 「A < B」は、差が測定誤差の大きさなら通ってしまう

右主気管支が左より短いことを `length(right) < length(left)` で固定していました。
実測 **1.457 対 1.446** ——正しい向きに 0.7%。**コイン投げが事実の顔をして**
2 か月通っていました。肺門を表面に載せ直した瞬間に左右が入れ替わり、
そこで初めて分かりました。

順序が主張なら、**主張に足るだけの差**を書いてください
（`length(right) < length(left) * 0.95`）。差が出ないなら、それはモデルが
その事実を持っていないということで、テストを緩めるのではなくモデルを直すか、
持っていないと書くところです。

### H. コンポーネントに渡す形は、**渡す側**ではなく**読む側**から書く

`LearningPanel` に渡すモジュールの形を、シーン側で「こう書けば読めるだろう」と
決めて書きました。パネルが実際に参照するのは `option.label` なのにシーンは
`text` を書き、`setup.progress` に数値を期待するところに文字列を渡し、
`manipulation.control` に、`setModelControl` が知らない名前を書きました。
**テストも同じ想像の契約に対して書かれていた**ので、最後まで緑でした。
壊れたのはボタンを最初に押した読者の画面です。

このブランチだけで **5 回目**です（§5.10 の 12・15・19）。共通しているのは
「テストの assertion を、消費側のコードではなく自分の頭の中の仕様から引いた」
こと。**消費側が `x.y` と書いている場所を読んで、そこから assertion を引いて
ください。** 同じコンポーネントを既に使っている別のシーンがあるなら、
その形と突き合わせるのが最短です（`CopdScene` がそれでした）。

「名前の通りのことを測っていないテスト」は、無いより悪いです。無ければ
危ないと分かりますが、あると安全だと思い込みます。

### I. マスクは、その要素の `position: fixed` の子孫も一緒に巻き込む

スクロールする列に「まだ下がある」というフェード（`mask-image`）を足したところ、
**電話サイズでヘッダーの操作 4 つが canvas の下に沈みました**——ブランド・お気に入り・
サインイン・カタログ。理由は 1 行です。**`mask-image` は要素に stacking context を作り、
その中には `position: fixed` の子孫も含めて描かれます。** グローバルナビは `fixed` で
ビューポートに貼り付いていますが、DOM 上の親はたまたま `.top-left` でした。
親をマスクした瞬間、ナビはその stacking context の中に落ち、canvas が上に来ます。

`elementFromPoint` で測ると 320×568 / 375×812 で 4 つとも
`covered by canvas`、マスクを切ると 4 つとも `ok`。**CI の `verify:ui` が捕まえ、
同じスクリプトのローカル実行は捕まえませんでした**（Chromium のビルド差）。
つまりこれは「ローカルで緑だから安全」が効かない種類の欠陥です。

`transform` / `filter` / `perspective` / `backdrop-filter` / `contain` /
`will-change` は *fixed の containing block* を作るのでよく知られていますが、
`mask` は containing block は作らないのに **描画だけは巻き込む**ので、
レイアウトを測っても異常が出ません。位置は正しく、サイズも正しく、
ただ触れないだけです。

**エフェクト（mask / filter / opacity < 1 / mix-blend-mode）を要素に足すときは、
その部分木に `position: fixed` が居ないかを先に見てください。** 居るなら、
エフェクトを足す側ではなく **fixed の側を外に出す**のが正解です——`fixed` の親は
描画順の決定であってレイアウトの決定ではないので、動かしても位置は変わりません。

### J. 対になった臓器では、フレームの中心に何も無い

hero のキーボード操作は「画面中央にあるものを名指す」でした。脳・心臓・肝臓では
正しく動きます——どれも中央に実体があるからです。**肺で黙りました。**

```
keyboard (desktop, lungs): Enter named "色分けされた部位をクリックすると…"  ← ヒント＝何も選ばれていない
  ...after turning Enter named "左上葉 左肺 › 肺葉 › 葉"
```

左右の肺のあいだは縦隔で、**フレームの中心はその隙間に落ちます**。回してから押すと
動くので「たまに効かない」ように見えますが、原因は決定的です。肺シーン自身の
`verify:anatomy` でも `(0.50, 0.44)` は空振りし、気道は `(0.50, 0.34)` にありました。

**これは肺の癖ではありません。** 腎臓の hero は左右を `x = ±0.72` に置くので、
公開すれば同じところで黙ります。対になった臓器・正中に管腔や間隙を持つ臓器は
すべてこの形です。

- **中心を最初に試し、空なら外へ広げる。** 中心に何かあれば必ず中心が勝つので、
  既に公開している臓器の挙動は 1px も動きません
- **広げる範囲は狭く保つ。** 隅にある構造は「目の前にあるもの」ではありません
  （実装は短辺の 32%）
- **見える約束を一緒に直す。** 照準のレティクルは中央に留めたまま、説明文を
  「画面中央**にいちばん近い**部位」に変えました。レティクルを実際の命中点へ
  動かす案は採りませんでした——`src/scenes/` に触れると公開 3 シーンの
  source digest が動き、**公開判断の記録を取り直すまで β が閉じる**からです
  （実測: model card 32 件が stale になりました）。`selectAtCanvasPoint` だけで
  済ませたのはそのためです
- 捕まえるもの: `npm run verify:hero-input`（公開臓器ごとに 1 回）と
  `tests/landing.test.js` の `hero aim:` 単体テスト。後者は
  「中心を先に試す」「外へ広げる」「隅まで行かない」の 3 つを別々に壊して
  赤を確認済み

## 3. 回帰ハーネス

数値テストが全部通ったまま出荷された不具合が、この文書に何度も出てきます。
`npm test` は「値が正しいか」を見ますが、**その値が正しい対象に付いているか**は
見ません。`artifacts/visual-qa/` に 2 本置いてあります（どちらも Playwright が要るので
リポジトリの依存には入れていません）。

| | 対象 | 例 |
|---|---|---|
| `uicheck.mjs` | DOM。4 viewport | ラベル重なり、トラック内収まり、低 viewport の非表示、言語往復、console error |
| `scenecheck.mjs` | 実行中のシーン | マテリアルが全状態で意図の値か、実描画画素の輝度関係、白飛びの有無、ラベルが canvas 内か |

`scenecheck.mjs` の作り方で効いた点：

- **組み立て済みアプリを駆動する。** コンポーネントを単体で作って質問するのでは、
  「constructor では正しく 1 フレーム後に壊れる」種類の不具合を取り逃します。
- **実描画画素を測る。** ジオメトリから投影した点でサンプルし、
  `composer.render()` の直後に 2D canvas へ `drawImage` して読みます。
- **白飛びガードは回帰ガードとして置く。** 現在値のすぐ上に閾値を置き、
  「今より熱くなったら落ちる」ようにします。目標値ではありません。

ハーネス自身も間違えます。完了画面のショットをトラック 99.5% のクリックで
撮っていたところ、完了行が出た後はその位置に主 CTA が来るため、
**クリックが「自由操作に戻る」に当たって別の画面を撮っていました。**
静かに違うものを測るテストは、この文書全体が扱っている失敗そのものです。
